현재 명세의 공고 추천·이미지 분석과 위 항목은 이름만 바꿔 동일하다고 보지 않는다. 기능 정의 차이가 남으면 이 대조표와 실제 결과를 제시해 평가 기준과 맞춘다.

## RAG 코드 재현

- ai/retrieval.py: search_documents는 knowledge.json의 sections 및 저장 공고 본문을 문서화한다. rank_documents는 모든 본문의 TF-IDF로 순위를 계산한다.
- ai/agent.py: respond의 initial_evidence 및 도구 결과가 최종 LLM messages에 전달된다.
- tests/test_agent_api.py: test_new_document_body_is_searchable_without_editing_keywords는 새 문서의 고유 단어를 코드 키워드 수정 없이 찾는지 검사한다. 도구 왕복 테스트는 결과가 모델에 전달되는지 검사한다.
- 이는 소규모 로컬 자료집 검색이다. 임베딩 검색·실시간 원문 수집·모든 답변의 정확성을 주장하지 않는다.

## 배포 후 절차

1. Render 배포의 Source가 이번 수정 커밋인지 확인한다. /health의 revision도 비교한다. health 성공은 LLM 호출 성공을 뜻하지 않는다.
2. `py -3 tools/verify-reevaluation.py` 실행. 실제 AI 요청 12건을 순차 전송하며 사용량이 발생한다.
3. 생성 JSON의 answer·sources·trace를 읽고 기능별 3회 중 2회 이상 기대 결과인지 사람이 판정한다. 자동으로 pass를 쓰지 않는다.
4. 실패한 요청의 request_id를 Render Application logs에서 검색한다. chat_unexpected_error의 category·frames를 같은 시각에서 확인한다. 입력·키·인증 헤더를 공유하지 않는다.
5. 인증·사용량·모델 설정 문제는 서버 설정/공급자 계정에서 해결한다. 이번 코드 수정만으로 키 폐기나 권한을 변경할 수 없다.
6. 새 결과를 원문 그대로 저장하고 실패도 보존한 뒤 재평가를 요청한다.
